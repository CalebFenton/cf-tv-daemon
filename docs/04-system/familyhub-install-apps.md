# Installing your own code on the panel

2026-11-26. This is the question that matters: not a web page, actual programs.
Status of every route found, including one conclusion of mine that was too
strong.

## Bottom line

**No published method exists.** Nobody has published installing a third-party
app on a Family Hub panel. That is a statement about the record, not about
whether it is possible.

Three doors exist. None is closed. None is open. One of my earlier "closed"
verdicts was wrong and is corrected in §4.

## 1. Door one: the panel's own app installer

This is the most promising and it is the one I kept walking past.

Developer Mode on this panel lists:

- **`Tizen Store Server`**
- **`SES Update Client`**
- `Cloud Service`
- `FKP Server`

`Tizen Store Server` is a **URL setting for where the panel fetches apps**. The
panel already installs apps — it has a store and it self-updates them. So the
installer exists and works. The only question is what it accepts.

On a TV, the equivalent works like this, and it is a supported developer flow:

1. Developer mode on.
2. Host PC IP entered in the TV's dialog.
3. A **distributor certificate** generated by Samsung's certificate extension,
   containing the device's **DUID**.
4. `tizen install -n app.wgt`.

The fridge's Developer Mode has no host-IP field and no SDB, so steps 2 and 4
are out. But step 3 — a signed package containing your code — is not obviously
out, and `Tizen Store Server` is where a package would come from.

**Two unknowns, both cheap to test:**

| question | how |
|---|---|
| Does `Tizen Store Server` accept an arbitrary URL? | open it, look for an editable field |
| Will Samsung's certificate tool issue a distributor cert for a fridge DUID? | needs the DUID; try the certificate manager |

If both are yes, you sign a `.wgt` and point the panel at it. That is a real
program with real code, not a web page.

To get the DUID: on TVs it is Settings → Support → About This TV → Device Unique
ID, or the Device Manager. On the fridge, the `eMMC Information` or
`Tizen Store Server` screens are the place to look.

## 2. Door two: physical

eMMC read/write plus UART gives a root shell, and with a root shell you install
whatever you want. This is the only route with a published precedent on a fridge
panel — doitaljosh, 2017 board — and it does not depend on anything Samsung
signs.

Cost: opening the panel, and the 2017 recipe does not transfer directly (that
unit was ext4 on an older generation; this one has the TV partition layout).

## 3. Door three: code execution via the browser

The panel runs Chromium 105. A renderer exploit gives `uid=5001` in the
`org.tizen.browser` sandbox, and from there an escalation primitive would give
root, and root installs apps.

I need to correct what I said about this. See §4.

## 4. Correction: I called CVE-2022-4262 absent, and that was too strong

I built a probe for the bug's root cause — whether the parser's sloppy-eval
scope decision flips across a bytecode flush — and it showed no variation on the
panel.

The problem: **it showed no variation on Node 24 as well**, and Node has the bug
fixed. So the probe cannot distinguish "fixed" from "not detectable by this
method" in either place. It produced the same answer in both, which proves
nothing about the panel.

What I can honestly say: **I could not confirm the root cause is present.** That
is weaker than "it is absent", and I stated it as the latter.

Two things also went wrong before that, both my errors: the first probe
scalar-replaced its own subject, and the second checked in the same job, where
`WeakRef`'s `KeepDuringJob` guarantees a "still alive" reading.

So the browser route is **unproven, not disproven**. Reopening it means getting a
real V8 primitive working, which needs the engine's internal object layout, which
needs either a leak or a debug build.

## 5. What to do next, in order

1. **Look inside `Tizen Store Server`.** It is a menu item on a screen you can
   already reach. If it takes a URL, that is the install path and everything else
   becomes unnecessary.
2. **Find the DUID.** Needed either way for a signed package.
3. Only if 1 and 2 fail, consider the physical route or returning to the browser
   work.

Step 1 costs a button press and I have not asked you to do it.
